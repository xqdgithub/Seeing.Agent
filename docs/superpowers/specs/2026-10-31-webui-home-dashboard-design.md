# WebUI 主页改版：卡片仪表盘（瀑布流）

- 日期：2026-10-31
- 状态：待批准（批准后进入实现计划）
- 范围：`samples/Seeing.Agent.WebUI`（仅前端页面与少量服务接线）

## 1. 意图与为什么

现状主页是「落地页」：大 logo + 标语 + 两个按钮 + 三张统计卡 + 一段「最近消息」。
它的问题不是好不好看，而是**信息价值低**：

- 「最近消息」只读**第一个会话**的最后 4 条，80 字硬截断、不可点击，属于伪数据；
- 内容区固定 `max-width: 800px` 居中，宽屏大片留白；
- 统计卡不可点；「开始对话」与「新建会话」在已有会话时行为几乎一致；
- 首页顺带把 `AppState.CurrentSessionId` 改成最近会话——不该由首页决定的副作用。

目标：把它变成**仪表盘**——错落卡片即入口，一眼看清「该处理什么 / 最近在哪聊 / 系统是否正常」，
点卡片进入对应页面。

## 2. 目标 / 非目标

目标：

- 采用用户选定的 **B · 瀑布流**（三列等宽、各列高低不一）承载卡片；
- 卡片即导航：点卡片进对应页面（列表型卡片支持行级跳转）；
- 数据全部来自现有服务，不新增后端接口；
- 窄屏自适应（三列 → 两列 → 单列）。

非目标：

- 不做实时推送/轮询（首屏快照 + 刷新按钮 + 返回页面时重载）；
- 不改侧边栏导航结构、不改模块路由；
- 不引入新的 UI 库或图表库；
- 不做深色模式专项适配（沿用现有主题）。

## 3. 方案选择（Approaches）

三版卡片布局草图已用浏览器预览对比：

| 方案 | 说明 | 取舍 |
|---|---|---|
| A · Bento 错落网格 | 12 列栅格，大卡 2×2 跨列跨行 | 密度最高、对齐严谨；但错落依赖卡片数量，数量少时容易塌 |
| **B · 瀑布流（已选）** | 三列等宽，各列高度由内容自然决定 | 视觉最「错落」；阅读顺序竖排，找信息稍慢 |
| C · 等高网格 | 3×2 等尺寸 | 最整齐可预测，但没有错落感 |

选择 B 的理由：用户明确要「错落排布」，且 B 的错落来自内容高度而非刻意跨行，
卡片增减时不会破坏整体结构。

## 4. 布局与响应式

> **修订（2026-10-31，用户看后反馈）**：改成「顶部恢复 Logo + 说明，下部等尺寸卡片网格」。
> 原方案（大 hero 删除 + CSS 多列瀑布流）在实机上卡片高度各不相同、排列显得零散，
> 用户要求「卡片固定一些尺寸」以便排布更好看。以下为**现行**描述，§3 的方案选择保留为历史记录。

- **顶部 hero（恢复）**：`ai.svg` 56px + 「Seeing」标题（主色 28px）+ 标语
  「行到水穷处，坐看云起时」+ 一行说明「会话、定时任务与待办审批一屏总览；点卡片进入对应页面。」
  + 两个大按钮（开始对话 / 新建会话）。「开始对话」优先续最近会话，无会话则进 `/sessions`。
- **次级条**：左侧「总览」小节标题，右侧「刷新」链接按钮——刷新与主操作分离，hero 只留主操作。
- **主体：等尺寸卡片网格**
  - `display: grid; grid-template-columns: repeat(auto-fill, minmax(260px, 1fr)); grid-auto-rows: 168px; gap: 16px;`
  - 卡片 `height: 100%; overflow: hidden;` → 同一行卡片等高、四边对齐，超出内容裁切（列表类卡片取前 3 条）
  - 断点：`≤900px` 最小列宽降到 220px（自动减列）；`≤600px` 单列且行高改 `auto`（避免手机端裁切）
- **卡片统一视觉**：白底、`8px` 圆角、`1px #e8e8e8` 边框、内边距 `16px`；
  hover 时边框转主色 + 轻微上浮（`translateY(-1px)`），暗示可点击。
- 卡片在 DOM 中的顺序即网格填充顺序：
  最近会话 → 待我处理 → 定时任务 → 会话 → 智能体 → 模型。

## 5. 卡片清单

| 卡片 | 内容 | 点击目标 |
|---|---|---|
| 最近会话 | 最近 4 个会话：标题、相对时间（如「2 小时前」）、运行中标记 | 行 → `/session/{id}`；「全部 →」→ `/sessions` |
| 待我处理 | 待审批数、待回答数、最近失败数（只显示非零项） | 整卡 → 打开「审批中心」抽屉 |
| 定时任务 | 接下来 3 次触发（名称 + 时间）+「已过期 N 个」 | 整卡 → `/cron-jobs` |
| 会话 | 会话总数 | `/sessions` |
| 智能体 | 主智能体数量 | `/agents` |
| 模型 | 可用模型数量 | `/models` |

「待我处理」在三项都为 0 时**整卡隐藏**，避免常驻噪音。

## 6. 数据来源（全部为现有服务）

| 卡片 | 来源 |
|---|---|
| 最近会话 / 会话数 | `ISessionDirectory.ListSummariesAsync()` |
| 智能体 | `IAgentRegistry.GetPrimaryAgentsAsync()` |
| 模型 | `ILlmService.GetAvailableModels()` |
| 定时任务 / 已过期 | `SchedulerStatusService.GetStatusAsync()` + `GetAllJobStatusesAsync()` + `JobExpiry.IsExpired` |
| 待审批 | `PermissionInbox`（现有 Singleton 投影） |
| 待回答 | `QuestionInbox` |
| 最近失败 | `JobNotificationService` 的最近失败事件缓存（若不可用则省略该项） |

## 7. 交互细节

- 列表型卡片：行点击 `stopPropagation` 进会话详情；卡片标题区点击进列表页。
- 空态：最近会话为空时显示「还没有会话，开始第一个对话」+ 新建按钮；统计卡不显示空态。
- 加载态：卡片区域用 `Skeleton` 占位，避免整页 Spin。
- 刷新按钮：重新拉取数据，局部重渲染，不整页 loading。
- **移除副作用**：首页不再写 `AppState.CurrentSessionId`。

## 9. 我做的判断（可推翻）

1. **去掉大 hero 与标语**：首屏让位给信息；「新建会话」保留在顶部工具条，主操作不丢。
2. **「待我处理」整卡打开抽屉**：审批中心是抽屉不是页面，直接跳 `/sessions` 帮不上忙。
3. **不做轮询/实时订阅**：首页常驻连接成本高；用刷新按钮 + 页面返回时重载足够。
4. **首版不做「工作区最近改动」卡**：其数据依赖会话事件流（`AgentFileChangeBridge`），
   在首页冷启动时不一定有内容，先不引入不确定性。
